Infraestrutura como Código

Da primeira máquina criada por código até uma arquitetura AWS completa - em 8 aulas, com siglas explicadas e aplicação direta no ToggleMaster.

Guia de estudo 8 aulas + glossário de siglas + arquitetura do Tech Challenge Atualizado em 2026-07-18

O que é Infraestrutura como Código?

É trocar uma sequência de cliques no painel da nuvem por uma planta escrita em código. Nessa planta descrevemos redes, servidores, bancos e permissões. O Terraform compara a planta com o ambiente real e calcula o que precisa mudar.

Por que combina com o nosso projeto

O Tech Challenge exige uma infraestrutura AWS completa e reproduzível. Com módulos Terraform, podemos criar VPC, EKS, bancos e serviços compartilhados de forma versionada, revisável e repetível, sem depender da memória de quem clicou no console.

Glossário - o significado das siglas

Os principais termos das oito aulas, explicados antes das partes técnicas.

As 8 aulas, uma a uma

Cada ficha apresenta a ideia principal, a utilidade, um caso de uso e a conexão com o Tech Challenge.

01

Introdução à IaC: Terraform e OpenTofu

Essencial no projeto
Em miúdos
Substitui procedimentos manuais por uma planta versionada. Terraform e OpenTofu leem essa planta e constroem o resultado declarado.
Siglas e termos
IaC, Terraform, OpenTofu, HCL, provider, resource, abordagem declarativa, main.tf, variables.tf e outputs.tf.
Para que serve
Criar ambientes mais rápido, sempre do mesmo jeito, com revisão, histórico e possibilidade de reprodução.
Caso de uso
Criar uma instância EC2 por código e depois repetir a mesma configuração em outro ambiente.
No ToggleMaster
Terraform será a ferramenta principal para provisionar a infraestrutura AWS exigida pela entrega.
02

Variáveis, Outputs e State

Essencial no projeto
Em miúdos
Variáveis são campos preenchíveis da planta; outputs são informações que ela entrega; state é o mapa que lembra tudo que já foi construído.
Siglas e termos
String, number, bool, list, map, object, variable, output, sensitive, state, backend remoto, lock e DRY.
Para que serve
Reaproveitar código entre ambientes, conectar módulos e colaborar sem perder o controle dos recursos.
Caso de uso
O módulo de rede recebe o CIDR e devolve os IDs das sub-redes para o módulo do EKS.
No ToggleMaster
O terraform.tfstate ficará em backend remoto S3, protegido e fora do Git; um mecanismo de lock evitará aplicações concorrentes.
03

Módulos, Loops e Condicionais

Essencial no projeto
Em miúdos
Módulos são peças de Lego; loops criam várias peças sem copiar código; condicionais decidem quando uma peça deve existir.
Siglas e termos
Root module, Terraform Registry, TofuHub, count, for_each, ternary, can, try, dynamic blocks e for expressions.
Para que serve
Separar responsabilidades, reduzir repetição e adaptar a infraestrutura a diferentes ambientes.
Caso de uso
Criar várias sub-redes ou regras de segurança a partir de mapas, mantendo um identificador estável para cada item.
No ToggleMaster
Usaremos módulos para rede, EKS, dados, mensageria, registros de imagem e IAM. Loops ajudam nos recursos repetidos, como repositórios ECR e bancos.
04

Automação com Terraform e GitHub Actions

Essencial no projeto
Em miúdos
A planta também passa por uma esteira de qualidade. Antes de mudar a AWS, ela é formatada, validada, analisada e apresentada para revisão.
Siglas e termos
CI/CD, GitHub Actions, workflow, PR, lint, fmt, validate, plan, apply, aprovação manual, auditoria e rollback.
Para que serve
Evitar execuções diferentes em cada computador e criar um processo previsível para mudanças de infraestrutura.
Caso de uso
Uma pull request publica o plano das mudanças. O apply só acontece depois da revisão e aprovação.
No ToggleMaster
Teremos uma pipeline própria para Terraform, separada das pipelines dos microsserviços, com gates antes de alterar a conta AWS.
05

Gerenciando Ambientes com Terragrunt

Opcional nesta entrega
Em miúdos
Terragrunt organiza muitas plantas e ambientes, permitindo que configurações comuns sejam herdadas em vez de copiadas.
Siglas e termos
Terragrunt, terragrunt.hcl, DRY, herança, inputs, dependency, generate, live, remote state e run-all.
Para que serve
Coordenar muitos módulos e ambientes em projetos grandes, reduzindo duplicação.
Caso de uso
Dev e produção compartilham região, backend e providers, sobrescrevendo somente os valores diferentes.
No ToggleMaster
É útil, mas adiciona uma camada de complexidade. Para a primeira versão da entrega, módulos Terraform bem organizados provavelmente são suficientes.
06

Kubernetes via Terraform

Usaremos em parte
Em miúdos
Terraform também pode criar objetos dentro do Kubernetes, escrevendo-os em HCL ou reaproveitando manifestos YAML.
Siglas e termos
Kubernetes Provider, Kubectl Provider, namespace, deployment, service, ConfigMap, Secret, RBAC, least privilege, Helm e ArgoCD.
Para que serve
Versionar recursos estáveis do cluster e reaproveitar objetos Kubernetes dentro do fluxo de IaC.
Caso de uso
Criar um namespace e instalar um componente fixo da plataforma depois que o EKS estiver disponível.
No ToggleMaster
Adotaremos o modelo híbrido recomendado pela aula: Terraform cuida do cluster e de componentes fixos; ArgoCD cuida das aplicações que mudam com frequência.
07

Auditoria, Versionamento e Segurança em IaC

Essencial no projeto
Em miúdos
Não basta automatizar. Precisamos saber quem mudou o quê, impedir configurações perigosas e guardar evidências de que as regras foram cumpridas.
Siglas e termos
Git, pull request, rollback, Terraform Cloud, Atlantis, tfsec, Checkov, OPA, Rego, Policy as Code, compliance e LGPD.
Para que serve
Encontrar portas abertas, recursos sem criptografia, segredos expostos e violações de políticas antes do apply.
Caso de uso
Uma política bloqueia qualquer bucket S3 sem criptografia ou banco exposto publicamente.
No ToggleMaster
A pipeline executará scanners de IaC e falhará diante de problemas graves. Os resultados também servirão como evidência da entrega.
08

Criando Infraestrutura Completa na AWS

Ensaio direto do projeto
Em miúdos
Reúne todas as peças anteriores para construir uma arquitetura real: rede, computação, dados, estado remoto, segurança, automação e documentação.
Siglas e termos
AWS, VPC, CIDR, sub-redes, AZ, IGW, NAT Gateway, route table, Security Group, EC2/EKS, RDS, S3, DynamoDB, IAM e OIDC.
Para que serve
Praticar o ciclo completo de planejar, modularizar, criar, proteger, automatizar e documentar uma infraestrutura profissional.
Caso de uso
Criar VPC com sub-redes públicas e privadas em duas zonas, EKS privado, RDS criptografado e pipeline autenticado por OIDC.
No ToggleMaster
É a aula mais próxima da entrega: ampliaremos esse desenho com os recursos específicos exigidos pelo enunciado do Tech Challenge.

Aplicação no Tech Challenge

Uma sequência prática para transformar o conteúdo do módulo na infraestrutura do ToggleMaster.

  1. Preparar o backend remotoCriar o bucket S3 e o mecanismo de lock antes de migrar o state para o uso compartilhado.
  2. Construir a redeUm módulo cria VPC, sub-redes públicas e privadas, Internet Gateway, rotas, NAT e Security Groups.
  3. Configurar identidades e automaçãoIAM e OIDC concedem ao GitHub Actions apenas as permissões temporárias necessárias.
  4. Criar a plataforma KubernetesO módulo EKS cria cluster e node groups nas sub-redes adequadas.
  5. Provisionar a camada de dadosTerraform cria três RDS PostgreSQL, ElastiCache Redis, DynamoDB e SQS conforme o enunciado.
  6. Criar registros de imagensRepositórios ECR recebem as imagens versionadas dos cinco microsserviços.
  7. Instalar componentes fixosTerraform ou Helm instala componentes de plataforma, como o ArgoCD, depois que o cluster estiver pronto.
  8. Entregar aplicações por GitOpsOs microsserviços ficam fora do state Terraform e são reconciliados pelo ArgoCD a partir do Git.
  9. Proteger cada mudançaPull requests executam fmt, validate, scanners e plan; o apply exige o fluxo de aprovação definido pelo time.
Divisão de responsabilidades recomendada Terraform controla a base relativamente estável da nuvem. Helm e ArgoCD controlam aplicações e releases que mudam com frequência. Essa separação reduz dependências no state e deixa o ciclo dos microsserviços mais simples.
